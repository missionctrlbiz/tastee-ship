# Validation — the coffee-shop case study

Reference: Nate Herk, **"I Told Claude to 'Make it better' 100 Times"**
(<https://www.youtube.com/watch?v=DByAR5Su1Yw>). Same fixture, same prompt
spirit ("look at the site, innovate, make one bold change that improves
conversions"), same dashboard ideas (rounds, milestones, LOC + cost trends,
site-preview scrubber) — plus the stop button the reference lacked.

> **Disclosure on models.** This validation ran in an environment with **no
> model API keys**, so the runs use tasteeship's **deterministic mock
> provider** (`mock-sonnet`, `mock-opus`) whose behavior profiles are
> calibrated to the video's findings: Sonnet = conservative small diffs;
> Opus = bold escalating diffs, a pumpkin-carving novelty feature, a broken
> language toggle, and a form regression. The harness treats mock proposals
> exactly like real ones — the gate, verification, kill switch, checkpoints
> and cost accounting are the production code paths. To reproduce with live
> models: `tship keys add anthropic` then
> `tship run --rounds 50 --provider anthropic --model claude-sonnet-5-5`.
> Raw evidence: `docs/evidence/*.json`, generated by `npm run validate`.

## Runs

Four runs against `examples/coffee-shop` (161 LOC baseline: Comic Sans, 980px
fixed layout, marquee, broken order form). `outputs_max = 4` everywhere.

| | run 1 — sonnet, gate=halt | run 2 — opus, gate=halt | run 3 — opus, gate=flag |
| --- | --- | --- | --- |
| status | **completed** | **halted @ r12** (over-build) | **completed** |
| rounds shipped | 50/50 | 12/50 | 50/50 |
| agent calls | 51 | 13 | 52 |
| tokens | 174k in / 32k out | 36k in / 8k out | 269k in / 55k out |
| cost (configurable rates) | **$1.01** | $1.92 | **$8.14** |
| final LOC | **425** (2.6× baseline) | 2,173 (13.5×) | **12,290** (76×) |
| clean / flagged rounds | 49 clean, 1 retry | 12 clean | 12 clean, 38 flagged |
| rejected attempts (gate) | 1 | 1 (the pumpkin round) | 2 |

## What the gate caught

| round | model | catch | gate action |
| --- | --- | --- | --- |
| r13 | opus | **pumpkin-carving configurator** — forbidden novelty feature (taste rule) | halted run 2 (`overbuild`), rolled back; flagged every later round in run 3 |
| r30 | opus | **language toggle that didn't work** — JS references DOM ids that don't exist | attempt rejected + rolled back; retry shipped a wired toggle (2 of 4 outputs spent) |
| r38 | opus | **form break** — refactor renamed the `#order-form` id out from under the form script | attempt rejected (critical selector), retry kept the stable id |
| r20+ | opus | **LOC drift** — cumulative LOC passed the 4,000 cap on the way to 12,290 | flagged per round in flag mode (over-build budget is a taste decision) |
| r21 | sonnet | footer removed (landmark regression) | attempt rejected, retry shipped the change intact |

## Where each model was "good enough"

- **mock-sonnet**: never tripped the gate in 50 rounds (one retry on its
  regression-drill round). Clean-ship streak = all 50. Cost $1.01, final site
  425 LOC — small, mobile-ready, working form. In the video's terms this is
  the profile that was "still usable at round 65"; here the gate never had a
  reason to stop it.
- **mock-opus**: good-enough window was **rounds 1–12** (clean-ship streak
  12): it fixed the form fastest, hit milestones earliest, shipped the boldest
  early changes — then went over-engineering. With the default gate it is
  **stopped at r12/r13 for $1.92**, ~24% of the flag-mode cost, with 2,173 LOC
  instead of 12,290. The unbounded run (flag mode, the reference video's
  regime) reproduced the video's pathology: 38/50 flagged rounds, novel
  features persisting, 76× LOC inflation.

**The gate, not the model, decides when to stop** — the case study's central
claim, reproduced: same fixture, same budget, two profiles, and the harness
picks different stopping points because it measures the repo, not the model's
confidence.

## Kill-switch drill (run 4)

1. Sonnet run in flight; `tship stop` issued while it was working on round 21.
2. Runner aborted the in-flight agent call, rolled the repo back to the last
   good checkpoint (`HEAD == lastGoodCommit` asserted), tree clean, run marked
   `killed / user-rejection`. Usage up to the kill was preserved.
3. Out-of-band edits after the kill are caught: `tship resume` refuses on a
   HEAD-vs-checkpoint mismatch until `--acknowledge --force` (resume verifies
   assumptions, per arXiv:2608.29381).
4. `tship resume --acknowledge --force` → completed all 50 rounds; usage
   accumulated across both phases (22 → 51 calls, $0.42 → $1.01).

## Cost notes

Costs use the configurable `costs` table in `.tasteeship/config.json`
(sonnet-class $3/$15 and opus-class $15/$75 per M in/out tokens). The mock's
per-call token counts are plausible simulations — treat the *ratios* (opus ≈ 8×
sonnet spend for the same 50 rounds, ≈ 29× LOC) as the finding, not the dollar
figures. With live keys the same accounting uses real provider usage data.

# Full test on the owner's own AI models (live)

`npm run live` reruns the case study on **the owner's own models**
(attached with their own keys through the standard `.env.local` injection):

| slot | model | provider |
| --- | --- | --- |
| light ("Sonnet" analog) | `zai-org/GLM-5.3-Flash` | RIVER (`api.river.ai`) |
| heavy ("Opus" analog) | `IFM/K2-Horizon-375B-A23B` (375B MoE) | IFM (`api.ifm.ai`) |

Each run: coffee-shop fixture, `outputs_max = 4`, gate = halt, real provider
tokens accounted per call. Costs are placeholder estimates — both models are
plan-included for the owner — so **tokens are the honest usage metric**.

## What the full test caught (v1, `docs/evidence/live-v1-*.json`)

The first live run halted **both** models at the gate — heavy at round 23,
light at round 16 — and the gate log showed why: not over-build, not
regression, but `protocol-error`s. The models emitted file contents with
**unescaped quotes and newlines inside JSON strings** (`"content": "html\n<div
id="order-form">…"`), which no strict JSON parser can read. Four unparbable
outputs later the outputs_max gate correctly stopped and reported instead of
forcing another change.

That is the kill-shot finding of a full test: **the harness bug surfaced as a
gate halt, not a crash or a silent bad ship.** The fix was made in the harness,
not the prompt — the change protocol now uses a line-based `SUMMARY:`/`FILE:`
block format (which cannot break JSON escaping) with JSON kept as a fallback,
and the parser got a two-stage implementation with unit tests.
